13 of your requirements

Pedro — the short version is that your workflow diagram is already implemented end to end, and the platform is already Avaya-native. The orchestrator was written directly against your diagram; its own header instructs developers not to add behaviour that is not on it.

All four workflow branches

Built

Answered/unanswered crossed with known/unknown caller, exactly as your diagram splits them. The branch is a first-class value in both the code and the database, so every call is stamped with which path it took and you can report on the mix.

server/call-workflow-service.ts · workflow_branch enum in migrations/0001

Pop-up on answered calls only

Built

The pop-up fires on answer and never on an unanswered call, matching the diagram's "No Pop-up Triggered" leg. Unanswered calls still run the full save-and-associate path without agent input.

Known caller: contact card from the number lookup

Built

The caller's phone number is looked up in HubSpot Contacts, the contact card renders from the match, and the company card is populated from that contact's primary company association — the behaviour your mock-up annotates.

Unknown caller: contact entry and company picker

Built

First name, last name and email entry, plus a typeahead company search. On save the contact is created in HubSpot and the chosen company is attached as Primary — the order of operations your mock-up specifies.

Live duration timer from answer

Built

The pop-up counts up from the answer timestamp, and the total is converted to milliseconds on save, which is the unit HubSpot stores. Unanswered calls save zero.

Support category sourced live from the ticket object

Built

Your requirement was "allow selection of SHP Support Category drop-down values from HubSpot Ticket Object". The dropdown reads the property straight from the ticket object at call time and filters hidden options, so the list can never drift from what SHP maintains in HubSpot. Nothing is hardcoded.

Ticket creation with subject, body and owner

Built

Tickets are created with a generated subject that distinguishes support calls from missed ones and flags unknown callers, and a body carrying received time, both numbers, answered state, duration, voicemail state and the agent's notes. The agent taking the call becomes the owner; on an unanswered call no owner is set, which leaves it Unassigned as you specified.

Pipeline routing, HH/HOS versus SNF

Built

Routing is data-driven through a rules table, matching on the dialled DID or on the selected support category, then falling back to a configured default and finally to the first pipeline with a loud warning. Because it is data and not code, changing how SHP routes is a configuration change.

Every association on the diagram, including the exception

Built

Call to contact, call to ticket, contact to ticket, and the contact's primary company to ticket. Your diagram's parenthetical — "except in case of unanswered + unknown" — is implemented as an explicit branch check, not left to chance.

Avaya IP Office as a first-class provider

Built

The provider is modelled through the stack, with the Avaya UCID as the call identifier and configuration for the TAPI line, CTI host, and credentials held per portal. Cloud-only surfaces such as SMS and per-minute billing are hidden automatically when a tenant runs on Avaya.

Voicemail and recording ingest from the appliance

Built

Built on the assumption your notes imply: TAPI reports the disconnect but never the media, so the appliance's voicemail and recording directories are watched, files are matched back to the call, and the URL is attached to the call activity. The directories, filename pattern and public base URL are all configuration.

Hunt groups with live agent state

Built

Groups, pilot numbers, members and extensions, with each member's current state and live counts of available and on-call agents for supervisors.

Local call log reconciled to HubSpot

Built

Every call is written locally with its HubSpot call, ticket and contact IDs. Deliberately, a local logging failure never fails the HubSpot write — HubSpot is treated as SHP's system of record.

Built, but differently from the documents

3 to confirm

Three places where the implementation makes a deliberate choice your documents leave contradictory. Each is working; we need you to confirm the choice rather than change code.

Voicemail Available is a custom property, not the HubSpot one

Confirm

Your sheet maps this to HubSpot's hs_call_has_voicemail, which is read-only — HubSpot derives it and the API will not accept a write. Rather than drop the requirement, the platform creates and writes its own voicemail_available property on the call object during onboarding, with Yes/No values, so you get the reporting you asked for.

ConfirmThe property name, if SHP wants something other than voicemail_available. It is configurable per portal.

Activity date is the answer time

Confirm

Your documents define this three ways — when logged, call start, and when answered. The build follows the workflow diagram: answer time on answered calls, arrival time on unanswered. Duration is measured from answer, so it is zero on a call that was never picked up.

NoteThis conflicts with the workbook's "Actual Start". If time-to-answer reporting matters, say so and we will store both.

Every call creates a ticket

Needs a ruling

The build follows your mock-ups, which state ticket creation unconditionally. Your workbook says the opposite for direct-extension dials — "If direct extension dial = Do not create ticket" — and that rule is not implemented.

As it stands, an internal desk-to-desk call would open a support ticket. This is the highest-impact open item in the set and it is question one below.

Call Outcome is not captured

Gap

Your pop-up marks Call Outcome required with six values, and your unanswered branch specifies "No Answer" when the call was not answered and "Left Voicemail" when a message was recorded. The pop-up has no outcome selector today, and hs_call_disposition is never written.

Call status is set correctly on every call, so the answered/unanswered distinction is safe — but the disposition your reporting will want is missing. Note also that the property currently has no options defined in the portal export you sent, and "Wrong number" is not a HubSpot default, so the value list needs creating before the field can be built.

Call and Meeting Type is not captured

Gap

Also required on your mock-up, with ten values from Training through Troubleshooting. Not on the pop-up and never written. Two things to settle first: the list contains an apparent duplicate — "AM -Introduction - Call" and "AM - Introduction Call" — and the export shows this property has never been populated on any call, so this is new behaviour for the team rather than a habit to preserve.

The report sub-category cascade

Gap

Only the single support category property is handled. The conditional cascade — selecting Portal Reports exposing SHP Portal Report Category and SHP Reports, with values varying by Segment Type — is not built, and the three sub-properties are not referenced anywhere.

Two blockers in your documents: the triggering value is written "Portal Reports" in the workbook and "SHP Portal Reports" on the mock-up, and Segment Type appears on the mock-up but in no mapping. A property export from your Tickets object settles both.

Company owner and Enterprise Number on the pop-up

Gap

Your company card specifies Company Name, Owner and Enterprise Number. The card currently shows name, domain and location. Adding the two missing fields is small — we need confirmation that enterprise_number_unique_2 is the live property, since the _2 suffix usually means an earlier one claimed the name.

Correcting a wrong contact match

Gap

Your known-caller mock-up has an Edit control that opens a contact search when the phone number matched the wrong person, and an Add New Contact path from there. The pop-up lets the agent change the company but not the contact. Worth building — a shared or reassigned number will otherwise log calls against the wrong record.

What we need from you

3 answers, 2 exports
  1. Does a direct-extension dial create a ticket? Your two documents disagree and the build currently creates one on every call. This is the one that changes daily ticket volume for your team.
  2. How is HH/HOS versus SNF actually determined — by the inbound DID, by the category the agent picks, or by the caller's company record? The routing engine supports all three; we just need to know which is authoritative. This question is flagged in the code as an open item awaiting your answer.

The ingest supports publishing them, but your callers are home health, hospice and SNF agencies, so those recordings should be assumed to contain PHI. Whether the link is public, expiring, or internal-only is a compliance decision, not a technical one, and we would rather have it in writing now.
  4. A property export from the Tickets object, matching the one you sent for Calls. It settles the category names, the exact cascade trigger value, Segment Type and the pipeline IDs in one step.
  5. The support-line table — every support DID and hunt group pilot number mapped to its segment. The routing rules are data, so this is the last thing standing between configuration and go-live.
