Requirements reconciliation

SHP Call Integration Review

Twenty-four items where the pop-up mock-ups, the property mapping, and the live HubSpot portal disagree with each other.

Sources Call Integration Property Details.xlsx · Popup and Workflow.pdf From Pedro Aguilar, SHP Reviewed 17 Aug 2026

How to read this

Both documents came from Pedro on 17 Aug 2026 and are the current requirements — there is no competing version to diff against. So the reconciliation runs three ways: the property mapping against the mock-up deck, and both of those against the portal's own property export, which sits in the workbook's second tab and is the authority on what exists and what can be written.

That makes every item below a question for Pedro rather than a discrepancy between his spec and someone else's. The seven read-only items are not judgement calls — the API will refuse them — and the eight contradictions each need one ruling from SHP before a developer can start.

Read-only properties

Items 1–7

The workbook's second tab, Ref-ALL HubSpot Call Properties, is an export of the 49 call properties as they actually exist in the portal, and its Read only value column is the authority here. Seven properties the spec asks the integration to write cannot be written. These are hard stops, not preferences — the API rejects them.

01Blocker

The voicemail flag cannot be set by the integration

This one is stated as an explicit instruction in the workflow, so it will fail loudly on the first voicemail. The flag is derived by HubSpot from the call's own voicemail data.

PDF workflow"If VM left, set 'Voicemail Available' property on Call Activity to 'Yes'"
XLSX mappingVoicemail available · hs_call_has_voicemail · enumeration
PortalRead only value: True. HubSpot defined. Fill rate 0.9961
ResolveDrop the write and let HubSpot derive it, or carry the flag in a custom property SHP owns.
02Blocker

Record source cannot be forced to "Integration"

Record source describes how a record was created and HubSpot stamps it from the creating credential. A call created through a private app is already labelled as integration-sourced; the instruction to set the value is both impossible and unnecessary.

XLSX mapping"Set property value to 'Integration' (Internal value name: INTEGRATION)"
Portalhs_object_source_label · Read only value: True · HubSpot defined
EffectNo action needed if calls are created via a private app token
03Blocker

Dynamics "Call From" is mapped to a read-only nickname field

The migration maps the Dynamics Call From field onto the caller's display name. That property is read-only and currently empty across the portal, so the name will not land.

XLSX mappingCall From → From Number Name · hs_call_from_number_nickname
PortalRead only value: True · Fill rate 0
Notehs_call_to_number_nickname has the same constraint
ResolveCaller name belongs on the associated contact, not on the call.
04Blocker

"The user who logged the call" cannot be recorded where the spec puts it

The mapping note against Activity created by reads "The User that logged the call in the pop-up integration". That property is read-only and will resolve to the integration user, not the rep — so every call will appear to have been logged by the connector.

XLSX mappingActivity created by · hs_created_by · "The User that logged the call in the pop-up integration"
PortalRead only value: True · HubSpot defined
Works insteadhubspot_owner_id (Activity assigned to) is writable
ResolveSet the rep as activity owner and treat "created by" as the connector's own footprint.
05Blocker

Inbound answer status is calculated, not assignable

The mapping carries this as a stored property to populate from the phone system. HubSpot computes it, and it is empty portal-wide today.

XLSX mappingInbound Call Answer Status · hs_inbound_call_answer_status
PortalRead only: True · Calculated: True · Fill rate 0
ConsequenceAnswered vs unanswered must be driven off hs_call_status instead
06Blocker

Five more mapped properties are read-only or calculated

Each of these appears in the backend tracking block as though the integration or the migration will populate it: hs_call_has_transcript, hs_voicemail_count (also calculated), hs_call_summary, hubspot_team_id, and hs_call_location — whose four values are additionally flagged HIDDEN and READ-ONLY in the portal.

The system-audit fields hs_createdate, hs_lastmodifieddate, hs_created_by_user_id and hs_updated_by_user_id are read-only too. That is fine if they are being read for reporting, but the sheet maps them from Dynamics Created On / Modified On / Created by / Modified by, which reads as an intent to write history across. Historical audit stamps cannot be preserved on migrated calls.

PortalAll nine carry Read only value: True
DecideIf Dynamics audit history must survive, it needs custom properties
07Blocker

The one custom property in the mapping does not exist yet

dynamics_call_reason is the only non-HubSpot property in the call mapping, and it is absent from the 49-property portal export — so it has not been created. Separately, its type is wrong for its content: it is specified as single-line text to hold what the sheet itself calls "the Dynamics phone call entity, Call Reason drop down". Text will accept any spelling and cannot be reported on cleanly.

XLSX mappingDynamics Call Reason · dynamics_call_reason · single-line text
PortalNot present. All 49 exported properties are HubSpot defined
RecommendCreate as a dropdown seeded from the Dynamics option set

Where the two documents contradict

Items 8–15

These are cases where the workbook and the mock-up deck give different answers to the same question. Each needs one ruling before build, and each is the kind of thing that quietly ships wrong.

08Conflict

Does a direct-extension call create a ticket?

The workbook is explicit that it must not. The mock-ups state ticket creation unconditionally, in the header of both the known-caller and unknown-caller pages, and the workflow's unanswered branch also creates a ticket with no line-type condition attached. This is the single highest-impact disagreement in the set: get it wrong toward the PDF and every internal desk-to-desk call opens a support ticket.

XLSX mapping"For Support line(s) = create ticket. If direct extension dial = Do not create ticket"
PDF mock-ups"Call Activity automatically creates a Support Ticket, and all known associations are then associated to that Support Ticket"
Agreed partBoth agree the ticket section of the pop-up hides on a direct dial
Ask PedroConfirm the workbook rule is correct: tickets only from support lines.
09Conflict

Activity date is defined three different ways

One writable timestamp, three incompatible definitions across the two files. Duration reporting and any "time to answer" metric depend on which one is chosen.

XLSX backend"HubSpot defines this as the date and time the call was logged"
XLSX pop-upActual Start → "the Activity date/time stamp would be the start of the call"
PDF workflow"Display Activity Date as Date/Timestamp from when the call was answered"
RecommendUse call start for hs_timestamp so inbound and outbound are measured the same way, and derive answer time from the phone system if it is needed.
10Conflict

Create date is annotated as the time the call took place

The workbook's note on hs_createdate says HubSpot defines it as "the date and time the call took place", directly opposite the note on hs_timestamp in the row above it. The portal's own description settles it: create date is when the engagement record was created, and it is read-only. On a backfill this will be the migration date, not the call date.

XLSX noteCreate date — "the date and time the call took place"
Portal"The date that an engagement was created" · Read only: True
EffectAny report grouped on create date will be wrong for migrated calls
11Conflict

The value that reveals the report sub-categories is named two ways

The conditional logic keys off one exact enum value, and the two documents disagree on what it is — and the workbook disagrees with itself, since its note says "Portal Reports" while the mock-up screen shows the selected value as "SHP Portal Reports". A mismatch here means the sub-category fields never appear.

XLSX mapping"based on selection of 'Portal Reports' in SHP Support Category"
PDF mock-up"If 'SHP Portal Reports' is value in the Support Ticket 'SHP Support Category' property"
NeededThe internal value from SHP's ticket object, not the label
12Conflict

The report category property is SNF-specific but the design covers both segments

Routing sends tickets to either the SNF or the HH/HOS pipeline, and the mock-up says report category values vary by segment. But only one report-category property exists in the mapping and its internal name is scoped to SNF. Either it is misnamed, or the HH/HOS counterpart is missing from the mapping.

XLSX mappingSHP Portal Report Category · portal_report_category_snf
PDF mock-up"conditionally displays values based on 'Segment Type'"
ScopeTwo pipelines in play: HH/HOS and SNF
13Conflict

Who picks the company on a new contact — the system or the rep?

The two documents describe opposite directions of association for the unknown-caller flow. It matters because on an unanswered or unknown call there may be no company to inherit.

XLSX mapping"Once saved, associate the new contact to the call's associated Company"
PDF mock-up"HubSpot Company record look-up. Associate to Contact saved" — the rep searches and picks
14Conflict

New-contact fields appear in the known-caller flow too

The workbook restricts first name, last name, phone and email to calls with no matching contact. The mock-ups show an Edit control on the known-caller card that opens exactly those fields, for the case where the phone-number match is wrong. The workbook's rule is too narrow to build from.

XLSX mapping"Only display on pop-up if call is not associated with existing contact in HubSpot"
PDF mock-up"Edit contact match made from the phone number… present look-up search box" → Existing Contact Search and Add New Contact
15Conflict

Duration is specified for display but absent from the form

The workflow asks for a live timer on the pop-up. Neither mock-up has a duration field — both show only From, To, Direction, Activity Date, Call and Meeting Type, Call Outcome and Notes — and the workbook files duration under backend properties not shown on the pop-up. Note also that the stored value is in milliseconds, so a timer reading in seconds needs converting on save.

PDF workflow"Display Duration as live timer from call answer and save total to Call activity"
PDF mock-upsNo duration field on either screen
Portalhs_call_duration — "duration of the call, in milliseconds" · writable

Missing, unspecified, or unresolved

Items 16–24

Nothing here contradicts anything — it simply is not written down anywhere in the two documents, and each one blocks a build decision.

16Gap

The phone system is never named

Both documents defer repeatedly to "values mapped from phone system", and the workbook hints the platform is changing — "Future use with the new phone system?" against the transcript flag. Everything feasibility-critical hangs on this: whether there is an answered event to trigger the pop-up, whether the hunt group or support line is exposed on the inbound leg, whether a voicemail recording URL is retrievable, and whether a call-answered webhook exists to start the timer.

BlockingName the platform and confirm its API exposes answer events, line identity, and voicemail URLs. Until then the pop-up trigger is undesigned.
17Gap

No support-line to pipeline mapping table exists

Routing is specified in prose — SNF support line to the SNF pipeline, HH/HOS support line to the HH/HOS pipeline, direct dial to neither — but no document lists the actual numbers. This table is a prerequisite for items 8, 12 and 24, and only SHP can supply it.

RequestEvery support DID and hunt-group number, mapped to its segment and pipeline.
18Gap

Ticket pipeline, stage, subject and owner are never mapped

The ticket rules describe pipeline routing and assignment, yet the mapping's ticket section contains only the four category properties. There are no rows for the pipeline itself, the starting status, the ticket subject line, or the ticket owner — despite the workflow instructing that the ticket be assigned to the employee taking the call, and set to Unassigned when the call went unanswered.

AddRows for pipeline, status, subject convention and owner. Also decide the call and ticket title formats — hs_call_title is writable but no convention is given.
19Gap

Unanswered calls produce tickets nobody can complete

The workflow triggers no pop-up for unanswered calls, known or unknown, but still creates a ticket. With no pop-up there is no rep input, so the category can never be set — the instruction to "set ticket category, if known" can never be satisfied on this branch. For unanswered and unknown together the ticket has no contact, no company, no category and no owner.

In practice that means a blank ticket for every missed call, wrong number and robocall that reaches a support line.

RecommendCreate on voicemail-left only, or auto-close no-answer tickets on a timer. Confirm which with Pedro before build.
20Gap

Outbound calls have no workflow

The mapping describes outbound behaviour for the number fields, and the assignment rule covers the employee "accepting or placing" the call — but the only diagram is titled Incoming Support Call Workflow and branches solely on answered and unanswered inbound. Whether an outbound call raises the pop-up, and whether it can create a ticket, is undefined.

21Gap

Call status has no rule, and the outcome list is unverified

Only Call Outcome gets values in the workflow. hs_call_status sits in the backend block with no instruction, though it is writable and is the property that actually distinguishes Completed from Missed, No Answer and Busy — the same distinction item 5 shows cannot come from answer status.

Separately, the portal export shows no options defined for Call Outcome, while the mapping lists six. "Wrong number" in particular is not a HubSpot default, so at least one value needs creating.

XLSX mappingBusy · Connected · Left live message · Left voicemail · No answer · Wrong number
Portalhs_call_disposition · Options column empty · External options: True
22Gap

Segment Type is required by the logic but missing from the mapping

The mock-ups make report-category values conditional on Segment Type, which appears nowhere in the property mapping — not on the ticket, the company, or the call. Which object holds it, and whether the pop-up must read it at call time, is unanswered.

23Gap

Required fields and association labels are only in the mock-ups

The deck marks Call and Meeting Type, Call Outcome, SHP Support Category and the sub-categories as required with an asterisk; the mapping records no required-versus-optional state at all. The known-caller card also shows "Contact label: Primary", implying association labels on the call-to-contact link, which the mapping does not carry.

Required-ness also collides with item 19: fields cannot be mandatory on a form that never opens.

24Gap

Four open questions and some housekeeping the sheet is carrying

Left unresolved in the workbook's own notes: whether a call placed or answered from the help desk creates a ticket; whether the Dynamics Call Reason needs a synced property on the call activity; and which items are phase 2 — transcript and call summary are annotated as future use but sit in the phase-1 mapping.

Housekeeping worth fixing while the sheet is open: hs_call_has_transcript, hs_createdate and hs_created_by_user_id each appear twice in the mapping with different notes; the Call and Meeting Type list contains near-duplicates "AM -Introduction - Call" and "AM - Introduction Call"; enterprise_number_unique_2 carries a _2 suffix that usually means an earlier property took the name, so confirm it is the live one; and Dynamics Regarding is mapped only to Company, though it can point at a case or other entity and those references would be dropped.

What I would settle first

  1. Name the phone platform (16) — it decides whether the pop-up trigger, the live timer, and hunt-group detection are buildable at all.
  2. Rule on direct-dial ticket creation (8) and unanswered-call tickets (19) — these two shape the ticket volume SHP lives with every day.
  3. Get the support-line table (17) — nothing about routing can be built without it.
  4. Strip the seven read-only writes (1–7) from the mapping and re-issue it, so the build sheet stops describing impossible behaviour.
  5. Pin the exact enum values for support category and its sub-categories (11, 12, 21) from the live ticket object rather than from either document.
